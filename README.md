## 1. Запуск и использование

```bash

uv run algo

# Отдельные подкоманды CLI
uv run algo fib 10
uv run algo sort --algo both --dataset random --size 20

uv run algo gen --type nearly_sorted --size 15
uv run algo bench --repeats 3
uv run algo test all
```

### Интерпретация
1. **Поведение `insertion_sort`**:
   - На уже отсортированном наборе (`sorted`) алгоритм работает за линейное время $O(n)$, так как внутренний цикл `while` завершается на первом же сравнении. На размере 10 000 он опережает `heap_sort` в ~23 раза (0.0024 с против 0.0556 с).
   - На почти отсортированном наборе (`nearly_sorted`) сортировка вставками также остаётся эффективной (0.5913 с на $n=10\,000$).
   - На случайных данных, обратном порядке и массивах с дубликатами проявляется квадратичная природа алгоритма: время растет пропорционально $n^2$, и при $n=10\,000$ превышает порог 3 секунды.
2. **Поведение `heap_sort`**:
   - Пирамидальная сортировка демонстрирует стабильное время порядка $O(n \log n)$ независимо от упорядоченности данных (~0.05 с при $n=10\,000$ на всех типах наборов).

## 4. Вопросы к защите

1. **Сложность эффективной сортировки (`heap_sort`)**:
   - **Построение кучи (heapify)**: начинается с середины массива $n/2 - 1$ до корня. Сумма глубин вершин дает $\sum_{h=0}^{\lfloor\log n\rfloor} \lceil n / 2^{h+1} \rceil O(h) = O(n)$.
   - **Фаза сортировки**: $n-1$ раз корень (максимум) меняется с последним элементом и просеивается вниз на глубину не более $\log n$. Суммарно: $O(n \log n)$.
   - Итоговая временная сложность: $O(n) + O(n \log n) = O(n \log n)$ в лучшем, среднем и худшем случаях. Память — $O(1)$ (in-place).
2. **Инвариант структуры данных в виде теста**:
   - Реализован тест `test_stack_lifo_invariant` в `tests/tests.py`: проверяет, что каждый `push(x)` увеличивает размер на 1, `peek()` возвращает $x$ без изменения состояния, а последовательные `pop()` возвращают элементы в точности в обратном порядке добавления, опустошая стек до исходного состояния.
3. **Почему бенчмарк нельзя выполнять на одном изменяемом списке**:
   - In-place алгоритмы изменяют порядок элементов в исходном списке. При первом же прогоне список станет полностью отсортированным. Все последующие повторы будут замерять время работы не на исходном наборе (например, random или reversed), а на уже отсортированном. Для сортировки вставками это исказит время с $O(n^2)$ до $O(n)$ (с секунд до долей миллисекунды). Поэтому перед каждым замером создаётся независимая копия (`sample = data.copy()`), не включаемая в замер таймера.
